Design review, as automatic as the linter

For the last few weeks a Claude plugin has been checking every UI change I make against our design system, and fixing what it can. It works. This page proposes how to make it part of the workflow for everyone contributing to docusketch-frontend — and asks for a decision on three points.

What I'm asking for

Three decisions. Everything else on this page is the reasoning behind them.

Decisions needed

  1. Adopt the plugin as team tooling — move it into the docusketch organisation and enable it in the repo, so every developer gets it automatically instead of installing it by hand.
  2. Approve ~2 weeks of engineering to convert the mechanical rules into ordinary linter checks that block a merge for free, with no AI involved.
  3. Approve an advisory AI review on pull requests — a comment, not a block, to begin with. Budget in the order of $100–150 per month.

Nothing here changes how anyone writes code today. The first two items make the existing rules easier to follow; the third makes them visible in the place where review already happens.

Context

The problem, in plain terms

The Portal has a design system: a fixed set of buttons, colours, spacing, icons, form fields. When code follows it, the product looks like one product. When it doesn't, the drift is invisible in any single pull request and obvious once you open five screens in a row.

The rules are real

They exist, they're written down, and they're detailed. Nobody can hold 133 of them in their head while shipping a feature.

Review catches some of it

A reviewer looking at a diff sees logic and structure. A hardcoded colour or a wrong button variant reads as normal code.

Cleanup is expensive

Found later, the same fix costs a ticket, a branch, a review and a regression check instead of thirty seconds.

What exists today

The plugin, and what it actually does

One command. It reads the changed files, walks every rule, prints a table of what passed and what failed, and applies the fixes that are safe to apply automatically. Anything requiring a human or designer judgement it flags instead of touching.

The part that isn't obvious

The value isn't the pattern matching — it's the accumulated judgement. A single rule about hardcoded colours has grown sub-cases over months of real pull requests: a colour written as a fallback value, a token whose fallback disagrees with the token, a pale tint paired with a saturated token, an invented token name that silently renders the wrong colour. Each one was a real regression that got caught, understood, and written down.

That knowledge currently lives in one person's tooling. Making it shared is the point of this proposal.

The plan

Three layers, deliberately different strengths

One check can't serve everyone. A blocking gate has to be fast and never wrong; a smart review can be slower and occasionally debatable. So: three layers, each doing what it's actually good at.

1

While the code is being writtenThe plugin, enabled from the repository itself

The developer gets the feedback before the code is finished. Fastest, cheapest, least annoying moment to fix anything. Enabled by committing the plugin reference into the repo — no per-person setup.

Advisory
2

Mechanical rules in the ordinary linterESLint + Stylelint, in the CI checks we already run

Roughly 40 rules — hardcoded colours, off-scale sizes, retired components, raw Bootstrap classes — need no intelligence to detect. Moved into the standard linter they cost nothing per run, never disagree with themselves, and can safely block a merge.

Blocks merge
3

AI design review on the pull requestA new GitHub check that comments with its findings

Covers everything judgement-based that a linter can't express. Posts a findings table on the PR. Advisory at first — we only consider making it blocking once we can see its false-positive rate on real pull requests.

Comment only

We already have a working precedent for layer 3

The repo runs PR Safeness today: a GitHub check that asks Claude to assess each pull request, posts a score as a comment, and never blocks — the developer decides. The API key, the permissions and the shared workflow all already exist. Layer 3 follows the same pattern, which is why it's the cheapest of the three to build.

Feasibility

How much can actually be automated

Judgement
~73 rules		 “Does the button variant match the role of the action” · “one primary action per screen” · “error palette vs warning palette” · “tabs or a segmented control here” These require reading intent. No linter can express them — and this is precisely where the plugin earns its keep.

One constraint worth naming up front

We cannot switch these checks on across the whole codebase. Around 340 style files were written before these rules existed, and turning the rules on globally would light up the entire project in red. So enforcement applies only to lines a pull request actually changes — new code is clean, existing code is left alone until someone touches it. This is the same principle as the test-coverage gate we already run on pull requests.

Effort & cost

What it takes to build

One engineer. Layers can ship independently and in this order, so value arrives before the whole thing is finished.

  1. Day 1
    Move the plugin into the organisation and enable it in the repo

    Every developer gets the command without installing anything. Version-tagged so the rules can't shift under an open pull request. Cheapest step, largest immediate effect.

  2. Days 2–4
    Advisory AI review on pull requests

    Follows the existing PR Safeness pattern, so this is mostly plumbing. From here on, design findings are visible to reviewers on every PR.

  3. Week 2
    Mechanical style rules in the linter, changed lines only

    The style-file rules — colours, sizes, radii, shadows — plus the wrapper that limits enforcement to the diff. This is what makes the first checks genuinely blocking.

  4. Week 3
    Template rules and the handful of complex ones

    Raw Bootstrap markup, retired components, and the four or five most-violated rules that need real structural checks.

  5. Ongoing
    Exceptions register and rule upkeep

    A file in the repo recording every “yes, this one is intentional” decision, so it's argued once and never re-flagged. Needs a named owner.

Engineering

~2 to 3 weeks of one engineer's time, front-loaded. After that it's maintenance: adding a rule is a few lines, not a project.

Running cost

~$100–150 / month for the AI review, assuming we run it when a PR opens and is marked ready — not on every push. A full review costs a few dollars, so the trigger settings matter more than the price.

Risks

What could go wrong, and the answer to it

These are the objections I'd raise myself. Each one has a specific mitigation baked into the plan above.

RiskWhy it mattersMitigation
AI review isn't perfectly repeatable The same pull request can get slightly different findings on two runs. A gate that behaves unpredictably gets switched off or worked around. The AI layer never blocks a merge to begin with. Only the linter layer blocks, and linter rules are proven by their own tests and behave identically every time.
False positives erode trust One wrong complaint costs more goodwill than ten correct ones earn. This is the single most likely way the whole thing fails. An exceptions register in the repo: a decision is recorded once and stops resurfacing. Plus a named owner who resolves disputes rather than leaving developers to argue with a bot.
Cost creep Running the full review on every push, across many open pull requests, adds up fast. Trigger only on PR open and ready-for-review, only when the change touches UI files, plus an on-demand re-run by comment. Cost is a configuration choice.
Feedback arriving too late Finding a design problem in CI, after the work feels done, is the most irritating possible moment to find it. That's exactly why layer 1 exists. CI is the safety net; the real point of contact is while the code is being written.
Rules drifting apart Each rule would live in two places — the plugin and the linter config. Left alone, they diverge and start contradicting each other. Each rule is marked in the plugin with the linter check that enforces it, and a guard in CI fails if a rule loses its marker. We already run a similar guard on our AI configuration files.
Nobody uses it Optional tooling stays optional. Adoption is a people problem, not a technical one. Layer 2 is not optional — it blocks. Layer 1 requires no setup. Layer 3 makes findings visible to reviewers, so compliance becomes part of the conversation that already happens on every PR.

Discussion

Open questions for this meeting

Points I don't want to decide alone.

Who owns the rules?Once the plugin is team tooling, changing a rule changes everyone's checks. Does it need review, and whose?
Do we want a blocking gate at all, or is visibility enough?With PR Safeness we chose advisory. There's a real argument for watching how an advisory design review changes behaviour before tightening anything.
Who arbitrates “the bot is wrong”?The exceptions register only works if someone maintains it and can say no.
How many of the team work in an AI-assisted editor day to day?Layer 1 is only worth building if the answer is “most of us”. If it's two people, we skip it and lean on layers 2 and 3.
Which rules hurt most right now?I have a ranked list of candidates for the linter, but the team's own irritation is better data than my ranking. Bring the ones that keep coming up in review.
